# 繁體中文合成掃描 OCR 調查（2026-10-11）

## 結論與適用範圍

此問題是 **Tesseract 對特定中文行的混合語言辨識錯誤，且對頁面分割模式敏感**。
沒有證據顯示 UI 遺失整行、文字被裁掉、字型缺字或 CER 算法錯誤。
PSM 4 對既有單欄合成資料穩定有效；這不足以支持把所有文件強制改成單欄。
因此加入使用者可選的「單欄文件」，預設仍為自動版面 PSM 3。
本報告不宣稱一般真實文件的錯誤率為 37%，也不宣稱改動後 OCR 普遍無錯字。

## 錯誤分類

| 假設 | 觀察 | 判斷 |
|---|---|---|
| 應用程式漏行／排序 | 引擎原始 text 與校對行內容一致，四行都存在且順序正確 | 不是這次主因 |
| 缺字、裁切、低解析度影像 | 檢視實際 OCR PNG，第一行完整清晰；300 DPI 為 2400×1500，源圖 1600×1000，相當於 200 DPI，已有 1.5 倍放大 | 沒有缺字／裁切證據；放大不等於增加細節 |
| 影像前處理 | PSM 3 與 4 的 PNG SHA-256 相同；只改 PSM 即改善。200/400 DPI、Sauvola 均使第二頁退步 | 不需要改影像流程；不能把增 DPI 當通用改善 |
| 中英文辨識競爭 | PSM 3 首行變成 Latin；只用 chi_tra 時變成「葵體中文掃描測試」，只剩一字錯；交換語言順序無效 | 支持混合模型的辨識選擇參與錯誤，但不是語言檔未載入 |
| 版面／行分析 | PSM 4 完全正確；PSM 6 剩一字錯；PSM 11 退步。PSM 3/4 首行框均為 (153,152)–(771,227)，輸出 block／line 邊界相同 | 對分割模式敏感，但不是可見的漏行或框錯位置；不能據此斷言 Tesseract 內部某一項 heuristics 有 bug |
| 直排／表格偵測 | 單獨停用 vertical_text 或 find_tables 皆無變化 | 這兩個開關不能修正本例 |

PSM 3 首行 confidence 32，PSM 4 為 85。這只作診斷，沒有用 confidence 挑選答案、
更沒有把預期文字、字元白名單或 fixture 特例放入正式 OCR 程式。
要精確定位引擎內部語言選擇／字形正規化原因，仍需更底層的 Tesseract 偵錯；
目前證據足以確認可重現的模式差異，不足以證明某個內部函式是唯一根因。

## 程式與驗證

- 新增「文件版面」選單：自動 PSM 3／單欄 PSM 4，啟動時固定該次工作設定，忙碌時鎖定。
- 保留 300 DPI、3500 px 長邊上限、原生文字捷徑、語言資料、校對和輸出流程。
- 更新入口和 OCR 模組版本參數，讓網站更新後能取得一致版本。
- 原掃描測試擴充為兩個版面 × 兩個語言；兩種版面都實測逐行校對、跨頁儲存、
  未儲存修改捨棄、精確 TXT、PDF 隱藏文字層、逐像素不變以及匯回原生文字捷徑。
- CER 仍為 informational，沒有新增門檻、跳過、重試或允許失敗。
- 參數矩陣放在 opt-in 實驗目錄，不納入每次 CI；重跑方式：

  ```sh
  npm ci
  npx playwright install --with-deps chromium
  npm run test:ocr:compare
  npm test
  ```

實驗沿用 Playwright 與現有 server fixture，僅在實驗 context 中修改所載入的
OCR 模組參數並擷取引擎真實結果；不 mock Tesseract，不產生預設答案，不改磁碟正式程式。
正常功能回歸不使用這些注入。

本機驗證：Node **5/5**、Chromium 功能 **8/8**、選用參數比較 **2/2** 通過。
全部零跳過、零重試；自動模式保留基線 0.369565／0，單欄模式繁中與英文四頁均為 0。
