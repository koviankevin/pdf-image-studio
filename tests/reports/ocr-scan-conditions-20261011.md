# OCR 掃描條件與版面對照（2026-10-11）

## 實測結論

單欄 PSM 4 的優勢不能從乾淨控制頁推廣到低品質掃描。
本次固定條件下，只有乾淨控制頁比自動 PSM 3 好；傾斜、模糊、低對比兩者相同。
雙欄中文的字形全部辨識正確，但兩者都跨欄串成同一行，違反原稿預期閱讀順序。
因此保留現有模式與預設值，不調整正式 OCR 程式，也不以測試內容選擇辨識答案。

**全部是模擬掃描；實體掃描樣本數為 0。以下是六頁 fixture 的觀察值，
不是一般文件、中文 OCR 或實體掃描的準確率估計。**

## 方法與可重現性

- 基準為 PR #3 合併後 main：`54bd95e8517ba4cc986df1b96f4d54003c72c29e`。
- 沿用 Playwright 1.58.2、現有 server fixture、內附 PDF.js／Tesseract／語言資料。
  透過正式 UI 選 `chi_tra+eng` 與自動／單欄模式；沒有修改、替換或注入 OCR 模組。
- 源圖 1600×1000、52px 內附 Noto Sans CJK TC 字型、PNG 嵌入 576×360 pt PDF。
  源圖等效 200 DPI，正式流程以 300 DPI 產生 2400×1500 辨識圖，3500 px 上限未觸發。
  這個放大不會憑空增加源圖細節。PDF.js 確認所有輸入頁都沒有文字。
- 控制頁文字直接引用既有 `scanCases[0].pages[0]`。四種單欄劣化頁維持相同文字、
  字型、字級、頁面大小與行位置；每頁只改一項條件。雙欄是獨立版面樣本，
  不與單欄做內容相同的因果比較。未挑選最佳結果、未移除失敗條件。
- 兩種模式 × 六頁 × 預先安排三次獨立 browser context／worker = 36 次頁面辨識。
  同一次六頁工作重用正式 worker，保留真實多頁流程；沒有失敗後重試。
- 三次量測中每個模式的文字、框、CER、閱讀順序完全一致；所有模式／次數的源圖
  PNG SHA-256 相同。雜湊與完整資料見 [JSON](ocr-scan-conditions-20261011.json)。
- 此初始本機資料使用 Node 24.19.0／Chromium 153.0.8010.0（沿用先前暫存瀏覽器）。
  repo 的 Playwright 版本、依賴與正式 CI 安裝方式未變，雲端使用 Node 22 及其固定 Chromium。
  同一引擎的重複不等於跨設備或不同掃描來源驗證。

## 原始辨識文字與閱讀順序

JSON 的 `rawUiLines`／`actual` 是**校對前 UI 顯示的原始 OCR 行**，未人工修正或重排；
不是另行擷取的 Tesseract `data.text`。正式程式會 trim 每行首尾空白，再依引擎行順序顯示。
`boxes` 是逐行聚焦後 UI 的原稿標示框，單位為 PDF pt，保留原始輸出順序。
既有 `characterErrorRate`／NFKC／小寫／忽略空白、標點與符號完全未改。

部分具體錯誤（兩種模式相同，乾淨控制頁除外）：

| 條件／位置 | 原稿 | 原始辨識 |
|---|---|---|
| +1.5° 第一行 | 繁體中文掃描測試 | 繁髒中文掃描測試 |
| +1.5° 英文行開頭 | Synthetic | >ynthetic |
| 模糊第一行 | 繁體中文掃描測試 | 葵體中文掃描測試 |
| 模糊第二行 | 圖書館今天開放閱讀 | SiS ARAM Bae |
| 低對比第一行 | 繁體中文掃描測試 | Fans HSC tee Allaah |

雙欄預期先左欄 `L1,L2,L3,L4`，再右欄 `R1,R2,R3,R4`。
兩種模式皆輸出四個橫跨兩欄的框，文字如下（保留文字；本區塊縮短欄間空白以便閱讀，
JSON 完整保留 UI 原字串）：

```text
春天適合戶外散步      夏天注意補充水分
花園種植各種植物      公園設有休息座椅
閱讀可以增長知識      運動之後記得休息
今天一起練習寫字      明天繼續學習中文
```

本頁 64 個中文字都出現，但讀序是 `L1,R1,L2,R2,L3,R3,L4,R4`。
相對於指定的欄序，Levenshtein 距離 46／64，CER **0.718750**；
不能把它稱為「71.875% 的字形看錯」。也不能重新排序後宣稱本頁 CER 為 0。
這證明自動模式也不保證正確辨識雙欄，並非只有單欄模式有讀序風險。

`observeReadingOrder` 依固定源圖欄／行位置分類 UI 框，區分原稿順序、錯序、跨欄合併、
缺少或無法判斷。連續分片可合併成同一行的觀察，但不修改 OCR 文字或 CER。
這是本 fixture 專用觀察器，不適用任意文件；框順序符合也不表示文字正確。
單元測試刻意涵蓋跨欄、行交錯、缺行與未知框，避免漏字被誤報為順序正確。

## 使用上的證據與限制

- 已知乾淨單欄、中文被誤認為拉丁字元時，現有單欄選項仍值得比較；本控制頁支持這一點。
- 本次模糊與低對比兩種模式都出錯，切換單欄並不能修復這些樣本。不能由此估計更強或更弱
  模糊、陰影、曝光或壓縮的門檻；本次沒有做影像增強介入實驗。
- 多欄或未知版面仍保留自動模式作為起點，但這個稀疏、等行高且水平對齊的雙欄樣本
  連自動模式也失敗。重要文件須對照整欄閱讀順序，不能只看單字或 confidence。
- 本次只有單一字型、字級、單項劣化與一種稀疏雙欄。沒有實體掃描、手機照片、透視、
  紙張紋理、JPEG 雜訊、陰影、密集新聞雙欄、直排、表格、手寫或劣化組合。
- 真正實體掃描需另建來源清楚且經授權、無個資或已去識別的樣本，記錄設備與掃描設定，
  人工核對文字和閱讀順序，並標成 physical-scan；本次沒有把生成 PNG/PDF 充當實體掃描。

## 回歸測試與重跑

新增兩個日常瀏覽器案例，每種模式各處理六頁，保護劣化／跨欄辨識後仍可檢視有效框、
逐行人工校對、跨頁儲存與精確 UTF-8 BOM TXT 匯出。它們使用人工指定的校對字串作 oracle，
不以 OCR 答案驗證它自己。既有八個瀏覽器案例和五個 Node 案例原樣保留，
既有隱藏文字層、PDF 外觀不變及原生文字捷徑測試維持。

CER 和閱讀順序只寫入 informational 報告；不新增或放寬準確率門檻，
不將已知錯序設為必須持續錯誤的斷言，將來引擎改善不會反而讓功能 CI 失敗。
CI 延用零重試、零 skip，保存原始報告及生成的模擬 PNG/PDF 七天。

```sh
npm ci
npx playwright install --with-deps chromium
npm run test:ocr:conditions -- --repeat-each=3
npm test
```

本機預先安排量測 **6/6** 通過、Node **7/7**、完整 Chromium 功能 **10/10** 通過，
全部零跳過、零重試。既有英文與繁中控制組結果維持原值。
